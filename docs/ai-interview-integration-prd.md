# AI-Interview 接入需求文档

## 1. 文档目标

本文档用于定义如何把 [`nzy0510/AI-Interview`](https://github.com/nzy0510/AI-Interview) 中“动态面试 RAG / 题库工程化 / 面试准备 / 报告复盘 / Mentor 思路”接入当前“情景式教学系统 MVP”，并明确推荐落地路径、范围边界和验收标准。

## 2. 背景

当前项目已经具备：

- 文字/语音面试
- 三轮追问
- 五维评分
- 报告页
- 学习仪表盘推荐

但当前面试舱的核心约束仍然较强：

- 题目来源是固定种子 `InterviewQuestion`
- 追问更多依赖规则和已有题目字段，不是动态题库检索
- 没有独立的“面试题库管理”闭环
- 没有简历画像驱动的追问策略
- 没有独立的 AI Mentor 诊断页面

`AI-Interview` 的强项不在于“又多了一个面试页面”，而在于它把以下能力打通了：

- 面试准备中心
- 题库发布态与索引态分离
- 动态 RAG 追问决策
- 简历画像
- 历史报告 + Mentor 建议

## 3. 结论先行

### 已确认决策

已确认采用 **方案 A：能力迁移接入**。
- 已确认首期“面试题库管理”仅开放给 `admin`，不开放给 `instructor`。
- 已确认现有 `InterviewQuestion` 不作为首期主链路开场题来源，只作为兜底数据。
- 已确认首期每条题目至少必须包含 `principles + pitfalls + followUpPaths` 三个核心块，缺一不可。
- 已确认首期新题库统一同表存储，但必须用 `question_role` 区分 `opening / followup / mixed`。
- 已确认首期开场题选择不引入复杂推荐，先按岗位域、难度、题目角色和发布状态做简单可控筛选。
- 已确认首期题库导入只允许 `admin` 手工导入结构化内容包，不自动从案例工坊/UGC 回流。
- 已确认案例工坊与面试题库是两个独立模块，职责不同，不混用。
- 已确认首期题库导入流程采用三段式：`校验 -> 试运行/预览 -> 正式发布`。
- 已确认首期试运行/预览只做纯模拟，不写正式库。
- 已确认正式发布时同步触发当前批次的增量索引，同时保留手动重建作为修复入口。
- 已确认“可回滚的试导入”属于后续增强期，不纳入首期范围。
- 已确认索引失败时必须降级：开场题仍可从正式题库做普通筛选，追问检索回退到无题库上下文的现有规则链路，不能让整场面试不可用。
- 已确认首期底层 `difficulty` 继续沿用当前项目已有的 `L1-L5`，并允许管理端增加语义标签辅助理解。
- 已确认首期题库分类使用少量受控枚举，不接受自由文本分类。
- 已确认首期 `tags` 允许管理员自由填写，但系统必须做基础规范化。
- 已确认首期保留 `question_role = mixed`，但它只是例外类型，不是默认类型，数量需要严格控制。
- 已确认首期开场题与追问资源必须满足最低题量门槛；达不到门槛的 `category + difficulty` 组合不得直接开放。
- 已确认当 `category + difficulty` 组合题量不足时，首期直接不开放该组合，不使用旧 `InterviewQuestion` 填运营缺口。
- 已确认旧 `InterviewQuestion` 只用于真正的兼容/异常，不用于补题量、不用于补建设进度、不用于偷偷给用户兜底体验。
- 已确认一旦触发旧 `InterviewQuestion` 兼容兜底，状态只向管理员暴露，不向普通用户暴露。
- 已确认首期管理员侧对“兼容兜底触发”只做被动可见 + 可追踪，不强制实时处理。
- 已确认首期只开放少量高价值组合，优先为：`java + L2/L3`、`database + L2/L3`、`cache + L2/L3`、`ai_llm + L2/L3`。
- 已确认未开放组合在前端不显示；有题库、可用的组合才显示。
- 已确认导入包中的 `subject` 必须是稳定的“面试考察点标题”，不能直接写成自然语言题干。
- 已确认首期组合状态由后端根据题库实际状态返回，不写死前端。
- 已确认当“个人档案”里没有简历摘要/项目经历摘要时，前端只做中性提示“补充后更精准”，不做警告或阻断。
- 已确认首期导入包里的题目 `id` 必须稳定且全局唯一。
- 已确认首期导入包同时保留 `title` 与 `subject`，两者职责分开：`subject` 做稳定锚点，`title` 做展示标题。
- 已确认首期允许 `title = subject`，不强制两者必须不同。
- 已确认首期 `tags` 允许管理员自由填写，但系统必须做基础规范化（去空格、去重、统一命名）。
- 已确认首期 `followUpPaths` 至少 2 条，作为硬要求。
- 已确认首期 `principles` 必须足以支撑 1 次完整回答，不能只是关键词或占位提示。
- 已确认首期 `principles` 至少 2 条。
- 已确认首期 `pitfalls` 至少 2 条。
- 已确认首期 `pitfalls` 与 `followUpPaths` 必须保留顺序，顺序可以表达优先级。
- 已确认同一稳定 `id` 的题目再次导入时，按更新旧题处理，并保留版本历史。
- 已确认同一稳定 `id` 即使内容完全一样，再次导入时也仍然生成新版本记录。
- 已确认版本历史必须区分 `content_update`、`duplicate_import`、`manual_edit`、`restore_archived` 四种类型。
- 已确认首期开放“已发布题目编辑入口”，且编辑保存后直接生效：保留版本历史，但当前版本立即切换。
- 已确认在线编辑保存后先返回保存成功，索引异步补齐，并通过 `vector_status` 暴露 `pending / failed / indexed` 状态。
- 已确认在线编辑已发布题目时，必须复用导入链路的同一套硬校验规则，不能绕过字段、枚举和内容质量校验。
- 已确认在线编辑保存成功时，管理员必须填写简短编辑原因 / 变更备注，并写入版本历史和审计信息。
- 已确认在线编辑保存前需要轻量二次确认弹窗，但不引入复杂审批流。
- 已确认在线编辑已发布题目时不允许修改稳定 `id`；如需更换 `id`，应新建题目并归档旧题。
- 已确认在线编辑已发布题目时允许修改 `question_role`，但保存后必须立即重算题池归属与开放组合命中情况。
- 已确认在线编辑已发布题目时允许修改 `category / domain / difficulty`，但必须命中受控枚举，保存后立即重算开放组合。
- 已确认在线编辑已发布题目时允许修改 `subject`，但仍必须是稳定考察点标题，不能改成自然语言题干。
- 已确认在线编辑已发布题目时允许修改 `title`，且仍允许 `title = subject`。
- 已确认在线编辑已发布题目时允许修改 `sourceRef`，但必须非空，且只在管理端、版本历史和审计中可见。
- 已确认在线编辑已发布题目时允许修改 `principles / pitfalls / followUpPaths`，但必须满足数组、数量、顺序和内容质量硬校验。
- 已确认在线编辑普通表单不允许修改单题状态 `draft / published / archived`；状态变化继续走独立发布 / 归档动作。

### 推荐方案

推荐采用 **能力迁移 / 分阶段接入**，而不是把 `AI-Interview` 整个 Spring Boot + Vue 子系统原样挂到当前项目里。

### 不推荐方案

不推荐：

- 双系统并存
- 当前 Go/React 项目继续保留，另起一个 Spring/Vue 面试服务
- 在比赛演示环境中同时维护 MySQL、PostgreSQL、Qdrant、pgvector、两套用户体系、两套路由和两套管理后台

原因：

1. 当前项目已经有完整用户、面试、学习闭环与系统状态页，双系统会造成用户、报告、推荐链路分裂。
2. `AI-Interview` 依赖 `Spring Boot + MySQL + Redis + Qdrant + embedding-service + Vue`，与当前 `Go + React + PostgreSQL (+ pgvector)` 技术栈冲突明显。
3. 比赛项目更需要稳定、可控、可解释的增量接入，而不是大规模换底座。

## 4. 产品目标

- 与仪表盘联动
- 与用户画像联动
- 与学习推荐联动
- 与现有权限体系联动
- 与现有 AI Router / 系统状态页联动

## 7. 关键需求

### FR-01 面试题库实体

系统必须支持独立于当前 `InterviewQuestion` 的面试题库资源实体，至少包含：

- 稳定且全局唯一的题目 `id`
- 标题
- 主题/考核点（`subject`，要求是稳定的考察点标题）
- 题库分类（受控枚举）
- 岗位域 / 题目领域（受控枚举）
- 难度（底层继续使用 `L1-L5`）
- 标签（允许自由填写，但需基础规范化）
- 题目角色（`opening / followup / mixed`）
- 参考答案/要点
- 追问提示
- 发布状态
- 向量索引状态
- 来源信息（`sourceRef`，用于追溯）

### FR-02 发布态限制

只有已发布题库资源可以参与面试追问检索。

### FR-03 管理入口

首期只有 `admin` 可以在现有管理域内执行：

- 导入
- 预览
- 发布
- 归档
- 重建索引

首期最小必须动作集为：

1. 校验
2. 试运行 / 预览
3. 正式发布
4. 归档
5. 恢复归档
6. 重建索引

其中首期“检索预览”并入“试运行 / 预览”，不单独作为额外动作。

### FR-03D 导入流程

首期题库导入必须采用三段式：

1. 校验
2. 试运行/预览
3. 正式发布

管理员上传后不得直接入库生效。

### FR-03E 试运行边界

首期试运行/预览只做纯模拟，不写正式题库。

试运行允许：

- 解析导入包
- 校验字段
- 生成预览统计
- 展示会新增/更新哪些题目
- 展示会归档哪些题目
- 展示命中开放组合的统计
- 分开显示 `error_count` 与 `warning_count`
- 提供各自明细入口
- 展示 opening / followup / mixed 数量统计
- 单独显示内容质量拦截数量
- 单独显示结构字段缺失拦截数量

试运行不允许：

- 写入正式题库表
- 变更发布态
- 进入检索主链路

### FR-03F 发布后生效规则

正式发布后，系统必须：

- 写入正式题库
- 同步触发当前批次的增量索引

同时系统必须保留：

- 管理员手动重建索引入口

首期不要求：

- 可回滚的试导入
- 试运行数据回滚机制

### FR-03A 导入来源限制

首期面试题库仅允许 `admin` 手工导入结构化内容包。

首期不支持：

- 案例工坊内容自动转入面试题库
- UGC 自动发布为面试题
- 学员直接提交面试题库内容

### FR-03B 导入格式限制

首期唯一正式入库格式为标准 JSON 导入包。

后续可支持的原始素材来源包括：

- PDF
- DOCX
- TXT
- MD

但这些原始文档都必须先转换成标准 JSON 导入包，再进入管理员导入链路。

### FR-03C 数据清洗最低标准

首期每条题目至少必须包含以下三块内容：

- `principles`
- `pitfalls`
- `followUpPaths`

缺一不可。

首期不允许以下残缺数据进入正式题库：

- 只有题干，没有原理答案
- 只有标准答案，没有常见误区
- 只有题目和答案，没有可追问路径
- `followUpPaths` 少于 2 条
- `principles` 少于 2 条
- `principles` 只有关键词或占位提示，无法支撑一次完整回答
- `pitfalls` 少于 2 条
- `category` 不在受控枚举里
- `domain` 不在受控枚举里
- 结构齐全但内容明显重复、空泛、模板味过重

首期质量判断机制：

- 规则校验先拦截
- 管理员人工复核再确认
- AI 不作为首期主裁判

首期人工复核时，以下场景必须留发布备注 / 处理意见：

- 内容更新发布
- 重复导入但仍保留版本
- 结构勉强过线但需要人工确认
- 任何手动发布动作

### FR-03Z 批次内部分发布

首期允许：

- 同一个导入批次中
- 部分题目发布
- 部分题目暂不发布

首期不要求整批全量发布。

### FR-03AA 批次状态模型

首期批次状态至少应支持：

- `draft`
- `validated`
- `previewed`
- `partially_published`
- `published`
- `failed`

### FR-03AB 批次详情展示

首期批次详情页至少要展示每条题的：

- `id`
- `title`
- `subject`
- `category`
- `domain`
- `difficulty`
- `question_role`
- 单题状态

### FR-03AC 单题详情展示

首期管理员点开单题时，必须能看到：

- `principles`
- `pitfalls`
- `followUpPaths`

的原始结构化内容。

并且应直接显示这条题当前会进入：

- 开场题池
- 追问池
- 或两者都可

同时应显示：

- 这条题当前命中的开放组合
- 这条题未命中某些组合的原因

### FR-03AD 单题状态

首期必须保留单题状态。

也就是：

- 批次有批次状态
- 题目有题目自己的发布状态

系统不得只靠批次状态推断单题是否已发布。

首期单题状态至少应支持：

- `draft`
- `published`
- `archived`

其中 `archived`：

- 不参与开场题选择
- 不参与追问检索
- 但历史与版本仍然保留
- 首期不允许物理删除题目，只允许归档
- 归档时必须填写归档原因
- 可以恢复为 `published`，但必须走独立恢复动作、硬校验和二次确认
- 恢复归档题不用填写恢复备注
- 恢复时如果硬校验不通过，必须拒绝恢复
- 恢复归档题生成的新版本类型为 `restore_archived`
- 通过硬校验后立即恢复为 `published`，可进入后续新面试主链路
- 恢复后索引异步期间允许做开场题，追问增强等待索引完成
- `archive_reason` 必须进入版本历史和审计信息

其中 `draft`：

- 不参与开场题选择
- 不参与追问检索
- 只在管理端可见

### FR-03P 顺序保留

首期 `pitfalls` 与 `followUpPaths` 必须保留录入顺序。

顺序可以表达：

- 优先级
- 默认展示顺序
- 默认追问顺序

### FR-03H 题目 ID 约束

首期每条题目的 `id` 必须：

- 全局唯一
- 稳定不漂移
- 同一题目重复导入时仍使用同一个 `id`

系统必须能够基于这个 `id` 判断：

- 新增
- 更新
- 归档
- 索引同步
- 失败重试

同一个导入包内如果出现重复 `id`：

- 首期直接判错
- 不自动取最后一条
- 不自动覆盖

### FR-03Q 同 ID 导入策略

当导入包中再次出现相同稳定 `id` 时，首期应：

- 视为更新旧题
- 保留版本历史

即使内容完全一样，再次导入时也仍然生成新版本记录。

首期不采用：

- 一律拒绝发布
- 无版本历史的直接覆盖

### FR-03R 版本类型区分

首期版本历史必须至少区分：

- `content_update`
- `duplicate_import`
- `manual_edit`
- `restore_archived`

系统需要能让管理员明确看出：

- 本次是否真的改了内容
- 还是只是重复导入
- 是否由管理员后台在线编辑触发生效
- 是否由管理员恢复归档题触发生效

### FR-03R-1 版本存储模型

首期版本历史必须单独建表，建议为 `interview_knowledge_atom_versions`。

题目主表只保存当前生效版本：

- 当前可读字段
- 当前状态
- 当前索引状态
- `current_version`

版本表负责保存：

- 批次导入版本
- 在线编辑版本
- 重复导入版本
- 恢复归档版本
- 字段级 diff 摘要
- 审计信息
- 完整标准化题目快照

完整标准化快照至少包含：

- `id`
- `title`
- `subject`
- `domain`
- `difficulty`
- `category`
- `question_role`
- `sourceRef`
- `tags`
- `principles`
- `pitfalls`
- `followUpPaths`
- `status`

首期不放入快照的字段：

- `vector_status`
- `last_indexed_at`

首期审计信息与版本历史共表，不单独建审计表。

版本号规则：

- `current_version` 从 `1` 开始
- 每次版本事件单调递增
- `duplicate_import` 即使内容未变化，也推进 `current_version`

### FR-03R-2 版本并发控制

在线编辑提交必须携带 `base_version`。

保存时：

- 如果 `base_version` 缺失，拒绝保存
- 如果 `base_version != current_version`，拒绝保存并提示管理员刷新
- 如果匹配，则生成新版本并切换 `current_version`
- 如果主表 `current_version` 与版本表最新版本不一致，视为数据异常

首期冲突提示保持轻量：

- `版本已更新，请刷新后重试`

首期不做：

- 强制覆盖别人刚改内容的按钮

### FR-03R-3 版本写入函数复用

以下动作必须复用同一套版本写入函数：

- 批次导入
- 在线编辑
- 归档
- 恢复归档

目的：

- 统一版本类型
- 统一审计字段
- 统一 diff 摘要
- 避免不同动作产生不一致历史记录

首期不做：

- 回滚到历史版本
- 批量在线编辑多题

### FR-03S 已发布题目编辑入口

首期开放“已发布题目编辑入口”，且编辑保存后直接生效：保留版本历史，但当前版本立即切换。

当前要求：

- 管理端可以进入已发布题的编辑界面
- 保存后直接切换为当前正式生效内容
- 仍需保留版本历史和审计信息
- 历史会话继续读取会话快照，不被新版本反向污染
- 保存接口先返回成功，索引更新异步补齐
- 管理端通过 `vector_status` 展示索引状态：`pending / failed / indexed`
- 保存前必须复用导入链路的同一套硬校验规则
- 校验失败时不保存，并提示管理员修正
- 保存成功时必须填写简短编辑原因 / 变更备注
- 编辑备注写入版本历史和审计信息
- 在线编辑生成的新版本类型为 `manual_edit`
- 保存前需要轻量二次确认弹窗，提示“保存后将立即影响后续新面试，历史会话不受影响”
- 稳定 `id` 不允许在线编辑修改
- 如需更换 `id`，应新建题目并归档旧题
- 允许修改 `question_role`
- 修改 `question_role` 后必须立即重算题池归属与开放组合命中情况
- 允许修改 `category / domain / difficulty`，但必须命中受控枚举，并在保存后立即重算开放组合
- 允许修改 `subject`，但必须保持稳定考察点标题语义，不能改成自然语言题干
- 允许修改 `title`，且仍允许 `title = subject`
- 允许修改 `sourceRef`，但必须非空，且只在管理端、版本历史和审计中可见
- 允许修改 `principles / pitfalls / followUpPaths`，但必须继续满足数组、数量、顺序和内容质量硬校验
- 普通编辑表单不允许修改单题状态 `draft / published / archived`
- 允许修改 `tags`，但保存时必须 trim、去重、统一大小写或别名映射
- 即使内容没有实际变化，也生成 `manual_edit` 版本，并标记 `no_content_change = true`
- 版本历史和审计信息必须记录 `admin_id`、操作时间、`change_note` 和版本类型
- 保存字段级 diff 摘要，不保存复杂富文本 diff
- diff 摘要只记录字段名和摘要，不记录完整旧正文
- diff 摘要字段使用 `JSONB`
- `diff_summary` 只用于摘要展示，不承担恢复能力
- 保存时必须校验版本号；如果管理员基于旧版本编辑，拒绝保存并提示刷新
- 版本详情页显示 `no_content_change` 标记

这意味着首期不采用：

- 只开放入口但保存不生效
- 保存后长期停留在未生效草稿态
- 为等待向量索引完成而阻塞保存响应
- 允许在线编辑绕过 `principles / pitfalls / followUpPaths`、枚举、数量和内容质量要求
- 允许无备注修改已发布题目
- 复杂审批流或多人复核流程
- 在线编辑直接改写题目稳定 `id`
- 把发布 / 归档状态切换混入普通编辑保存
- 不留痕地忽略无内容变化的保存动作
- 覆盖基于旧版本提交的编辑内容

### FR-03N `subject` 约束

首期导入包中的 `subject` 必须满足：

- 表示稳定的面试考察点
- 可用于去重、归类、检索和统计
- 不直接写成自然语言题干

示例：

- 合法：`HashMap 扩容机制`
- 合法：`Redis 过期删除策略`
- 不合法：`请你讲一下 HashMap 为什么会扩容`
- 不合法：`如果 Redis key 过期了怎么办`

### FR-03O `title` 与 `subject` 分工

首期导入包必须同时支持：

- `title`
- `subject`

要求：

- `subject`：稳定的考察点标题，用于去重、归类、检索、统计
- `title`：面向管理端和前端展示的可读标题

系统不得：

- 用 `title` 代替 `subject` 做稳定识别
- 只保留其中一个字段

首期允许：

- `title = subject`

### FR-03T `questionRole` 继承规则

首期允许导入包顶层声明默认 `questionRole`。

规则：

- 单题未填写时，继承顶层默认值
- 单题显式填写时，以单题值为准

这样可以降低同类批次的录题成本。

### FR-03U `difficulty` 继承规则

首期允许导入包顶层声明默认 `difficulty`。

规则：

- 单题未填写时，继承顶层默认值
- 单题显式填写时，以单题值为准

### FR-03V `category` 继承规则

首期允许导入包顶层声明默认 `category`。

规则：

- 单题未填写时，继承顶层默认值
- 单题显式填写时，以单题值为准
- 无论顶层还是单题，值都必须命中受控枚举

### FR-03W `tags` 继承规则

首期允许导入包顶层声明默认 `tags`。

规则：

- 顶层 `tags` 作为公共标签
- 单题未填写时，继承顶层标签
- 单题显式填写时，与顶层标签做去重合并

### FR-03X 核心内容不允许批次继承

首期以下字段不允许使用批次级默认值：

- `principles`
- `pitfalls`
- `followUpPaths`

要求：

- 必须逐题显式填写

### FR-03Y 核心内容字段格式

首期以下字段统一使用数组格式：

- `principles: string[]`
- `pitfalls: string[]`
- `followUpPaths: string[]`

即使只有一条内容，也必须使用数组包裹。

### FR-03SA `sourceRef` 规则

首期必须保留 `sourceRef` 作为题目来源追溯字段。

并且：

- `sourceRef` 必填
- `sourceRef` 不能为空

首期允许：

- 导入包顶层提供统一 `sourceRef`
- 单题未填写时继承顶层值

但入库后：

- 每条题都必须有自己的 `sourceRef` 字段值

但首期前端用户界面：

- 不要求展示 `sourceRef`

首期后台/治理链路：

- 应保留并使用 `sourceRef` 做追溯、审计和批次核对

### FR-03I 最低题量门槛

首期每个 `category + difficulty` 组合至少应满足：

- `opening / mixed` 题目 >= 3
- `followup / mixed` 题目 >= 6

达不到门槛时，系统不得直接开放该组合进入主链路。

并且：

- 首期不使用旧 `InterviewQuestion` 去补题量不足的运营缺口
- 如果在线编辑导致组合低于最低题量，后端应自动关闭该组合
- 组合自动关闭后，普通用户不再看到该组合
- 管理端应显示警告，但首期不做消息推送

旧 `InterviewQuestion` 首期只允许用于：

- 迁移期兼容
- 明确的异常降级

一旦触发兼容兜底：

- 需要在管理员侧可见
- 不需要向普通用户暴露

首期管理员侧要求：

- 被动可见
- 可追踪

首期不要求：

- 实时告警
- 强制立刻处理

### FR-03J 首期开放范围

首期默认只开放以下 `category + difficulty` 组合：

- `java + L2`
- `java + L3`
- `database + L2`
- `database + L3`
- `cache + L2`
- `cache + L3`
- `ai_llm + L2`
- `ai_llm + L3`

其他组合首期不默认开放。

### FR-03K 未开放组合展示

首期未开放的 `category + difficulty` 组合在前端应：

- 不显示
- 不进入面试主链路

### FR-03L 组合状态来源

首期组合状态必须由后端根据题库实际状态返回，不允许写死前端。

前端只负责展示，例如：

- `available`

当在线编辑修改 `question_role / category / domain / difficulty / tags` 等影响组合命中的字段时：

- 后端必须重新计算组合状态
- 低于最低题量的组合自动从普通用户可见列表移除
- 管理端显示组合关闭原因和受影响字段

### FR-03L-1 索引状态治理

手动重建索引首期只允许 `admin` 操作。

管理端必须支持按 `vector_status = failed` 筛选题目，便于集中修复。

管理端还必须支持按 `version_type = manual_edit / restore_archived` 筛选题目或版本记录，便于审计人工变更。

题库列表默认隐藏 `archived`，但必须提供状态筛选查看 `archived`。

题库列表需要显示：

- 最近编辑人
- 最近编辑时间

版本历史列表要求：

- 默认按 `created_at DESC` 排序
- 展示版本号

索引失败时：

- 不影响开场题普通筛选
- 只影响追问检索增强
- 追问检索应回退到现有规则链路

### FR-03M 个人档案提示方式

当用户未填写个人简历摘要/项目经历摘要时：

- 前端可以给出中性提示
- 提示语义应偏向“补充后更精准”
- 不允许升级为错误、警告或阻断

### FR-04 动态追问

系统必须在每轮面试中，根据当前回答质量和检索结果决定下一轮策略，而不是只读固定追问字段。

### FR-04A 开场题筛选

首期开场题必须基于新题库的简单可控筛选产生，至少包含：

- `domain`
- `difficulty`
- `question_role in (opening, mixed)`
- `status = published`

### FR-04B 会话题目快照

创建面试会话时，系统必须保存当次开场题的题目快照。

快照至少包含：

- 题目 `id`
- 题目版本标识
- `title`
- `subject`
- `domain`
- `difficulty`
- `question_role`

作用：

- 历史会话回放不受后续题目编辑影响
- 报告复盘可以还原“当时实际问了什么”
- 管理端可追溯某场面试实际使用的是哪个题目版本
- 普通用户正在进行中的面试也继续使用会话创建时的开场题快照
- 在线编辑只影响后续新建面试的开场题选择

### FR-04C 追问知识原子轻量快照

每轮实际命中的追问知识原子，也必须保存轻量快照。

轻量快照至少包含：

- `atom_id`
- 版本标识
- `title`
- `subject`
- `domain`

首期明确不保存：

- 原子整段正文
- 大段 `principles / pitfalls / followUpPaths`

作用：

- 保证历史报告里的“为什么这样追问”不被后续改题污染
- 保留最小可审计证据
- 控制会话存储体积与上下文冗余
- 正在进行中的面试，后续轮次追问检索使用编辑后的实时题库内容
- 每轮命中的实时题库原子都必须保存当轮轻量快照

首期不要求复杂推荐算法。

### FR-05 弱召回回退

当检索结果弱、无效或向量侧异常时，系统必须回退到当前已有规则化追问链路，不能直接让面试失败。

### FR-06 报告增强

报告必须能体现“本场追问为什么这么问”，至少以摘要形式展示：

- 是否命中过题库上下文
- 追问类型
- 建议补强方向

普通用户报告页不展示题库版本号。

题库版本号属于治理信息，只在管理端、版本历史和审计视图中展示。

### FR-07 学习闭环联动

增强后的面试结果必须仍然回流到当前仪表盘与学习计划，不得形成独立孤岛。

## 8. 非功能需求

### NFR-01 稳定性

首期不得引入一套额外的强依赖运行时作为主链路前提。

### NFR-02 可维护性

优先复用当前：

- Go 后端
- React 前端
- PostgreSQL
- 现有 AI Router
- 现有鉴权与角色系统

### NFR-03 安全性

- 不泄露参考答案
- 不在前端暴露内部 prompt / 检索上下文原文
- 管理操作继续受现有管理员权限控制
- 首期 `instructor` 不参与题库导入、发布、归档和重建索引

### NFR-04 演示可靠性

比赛演示环境下，任何新增能力都必须支持：

- 降级
- 可解释
- 能在系统状态页观察到关键状态

### NFR-04A 索引失败降级

当向量索引不可用或当前批次索引失败时：

- 开场题仍可从已发布题库记录中按普通条件筛选
- 追问检索回退到无题库上下文的现有规则链路
- 不允许因为索引故障直接让整场面试不可用
- 管理端可通过 `vector_status = failed` 筛选失败题目并手动重建索引

## 9. 验收标准

### MVP 验收

满足以下条件即认为 MVP 成立：

1. 管理员可以维护一批面试题库资源。
2. 面试开始后，系统优先从新题库体系选择开场题，并基于当前回答和题库资源决定追问策略。
3. 检索失败时，系统能回退到现有规则链路。
4. 报告页可以看到追问依据摘要和建议方向。
5. 仪表盘推荐仍能消费面试结果。

## 10. 方案备选

### 方案 A：能力迁移（已确认，推荐）

把 `AI-Interview` 的题库、动态检索、准备页、报告思路迁入当前项目。

优点：

- 与现有系统一体化
- 维护成本最低
- 最符合比赛项目稳定交付目标

缺点：

- 需要重新实现，不是直接复用现成代码运行时

### 方案 B：外部子系统桥接

保留 `AI-Interview` 独立运行，通过网关/跳转方式接入。

优点：

- 见效快

缺点：

- 用户、权限、数据、报告、推荐全部割裂
- 运维复杂度大幅上升

### 方案 C：直接替换当前面试舱

把当前项目面试模块整体重构成 `AI-Interview` 的架构风格。

优点：

- 目标状态更完整

缺点：

- 改动面太大
- 不适合当前比赛项目节奏

## 11. 最终建议

如果目标是尽快把外部项目的价值吸进当前系统，最佳落地方式不是整仓接入，而是：

1. 用当前 Go/React 架构承接
2. 先落题库 + 动态追问
3. 再做准备页、报告和 Mentor 增强
4. 最后再评估是否需要更重的向量基础设施或用户级模型配置
