# 全项目代码审查后的优化顺序

## 目标

基于本轮全项目代码审查结果，明确后续优化与修复的实施顺序，优先处理安全和登录稳定性问题，再处理 HTTP 边界控制与前端构建体积问题。本文档用于指导后续增量实现，不代表这些优化会在一次提交中全部完成。

## 修改顺序

### 第一阶段：先收口认证阻断项

原因：当前认证链路仍存在高风险口子，继续叠加功能会扩大风险面。

预期收益：先消除账号接管和 JWT 弱配置问题，避免持久化环境在错误配置下继续运行。

- 下线或受控化匿名 `/api/v1/auth/password-reset`
  - 持久化模式默认禁用。
  - 仅保留 `/users/me/password` 自助改密链路。
  - 如果必须保留兼容接口，仅允许 `memory/dev` 模式显式开启，并在文档中标注“不适合生产”。
- 修正 `JWT_SECRET` 默认值策略
  - `docker-compose.yml` 不再提供仓库内固定弱默认值。
  - 持久化模式必须显式注入强 `JWT_SECRET`。
  - 启动失败信息继续保留明确提示，避免误判为其他故障。
- 改密后让旧 token 失效
  - 在用户模型或 claims 校验链路中引入密码版本或会话版本。
  - 改密后旧 access token 和 refresh token 都不能继续通过鉴权。

### 第二阶段：补齐密码体系一致性

原因：bcrypt 兼容已上线，但注册、改密和旧 hash 迁移仍不一致，长期会留下弱口令和旧 hash 存量。

预期收益：让密码校验和迁移逻辑闭环，减少历史包袱继续累积。

- 注册接口与改密接口统一密码规则
  - 拒绝空密码、纯空白密码和长度不足密码。
  - 注册和改密返回一致的错误语义。
- 登录成功后对 legacy SHA-256 hash 做透明升级
  - 仅在校验通过且识别为旧 hash 时回写 bcrypt。
  - 回写失败不能影响本次登录成功，但要有可观察日志或审计。
- 重新核对 demo 账户和 seed 数据
  - 保证 `demo / demo123`、`instructor / instructor123`、`admin / admin123` 登录链路不回归。

### 第三阶段：修登录稳定性与前端会话体验

原因：用户当前最容易感知的问题不是登录表单本身，而是 token 生命周期管理不完整导致的“用着用着失效”。

预期收益：让 Docker 后端常驻时的默认开发路径稳定，让真实用户在 token 过期后无需手动刷新页面。

- 前端请求层补 `401 -> refresh -> retry once`
  - 放在统一 `request()` 封装内。
  - 业务页不重复写刷新 token 逻辑。
  - refresh 失败后统一登出并回到登录页。
- 保持限流策略只统计失败登录
  - 成功登录不消耗失败配额。
  - 明确刷新、`/users/me`、登录成功和登录失败四条路径互不误伤。
- 明确本地启动约定
  - `pnpm run dev` 只启动前端。
  - Docker 后端作为默认配套环境。
  - 文档中写清 8080 端口占用预期，避免本地重复启动 Go 后端。

### 第四阶段：补基础 HTTP 安全与边界控制

原因：当前系统已经可用，但服务端读取超时、CORS 边界和公开端点约束仍偏演示态。

预期收益：在不破坏现有 SSE 和前端联调路径的前提下，把默认行为收紧到更稳的状态。

- 给 HTTP Server 增加完整的读取超时策略
  - 在不破坏 SSE 的前提下补足 `ReadTimeout` 或等效慢请求防护。
- 复核 CORS 和公开端点边界
  - 确认 `Access-Control-Allow-Origin: *` 是否仅用于本地演示。
  - 如果不是，仅允许前端实际开发源或部署源访问。
  - 明确 `/healthz`、`/system/ai` 等公开端点是否继续匿名开放。
- 复核 JSON body 限制与上传路径限制是否一致
  - 保证大文件只走上传链路。
  - 小 JSON 请求继续走 `decode()` 的体积限制，不互相覆盖。

### 第五阶段：做前端构建与体积优化

原因：当前构建仍有 chunk size warning，但这类问题不会先于认证安全和登录稳定性阻断系统使用。

预期收益：减少首包压力，降低重页面首次加载成本，同时不改动现有业务行为。

- 做路由级懒加载
  - 优先拆 `CommunityPage`、`InterviewsPage`、`SystemPage` 等重页面。
- 复核大依赖装载时机
  - Mermaid、图表、富预览等重量模块尽量延后加载。
- 重新观察 Vite chunk warning
  - 目标是继续压缩主包，但不为此引入额外业务回归。

## 每阶段验收

### 第一阶段验收

- 匿名重置口在持久化模式下不可用。
- 未设置强 `JWT_SECRET` 时，持久化后端无法启动。
- 用户改密后，旧 token 请求 `/users/me` 返回 `401`。

### 第二阶段验收

- 注册空密码、纯空白密码或短密码会被拒绝。
- 旧 hash 用户首次成功登录后，库中的密码会升级为 bcrypt。
- 现有演示账号登录链路保持不变。

### 第三阶段验收

- access token 过期但 refresh token 有效时，页面无需手动刷新可自动恢复。
- refresh token 失效时，前端能稳定回到登录态。
- Docker 后端 + `pnpm run dev` 的默认开发路径稳定可复现。

### 第四阶段验收

- 慢请求不会长期占住连接。
- 当前前端开发源仍可正常访问后端。
- 公开接口边界有明确文档，不依赖默认宽松行为。

### 第五阶段验收

- `pnpm test` 继续通过。
- 构建告警减少，首屏不回归。
- 登录后进入 `/dashboard` 的首屏交互保持稳定。

## 验证方式

### 自动化验证

- 后端
  - `go test ./internal/auth`
  - `go test ./internal/httpapi`
  - `go test ./cmd/server`
  - `go test ./...`
- 前端
  - `pnpm test`

### 手工验证

- `demo / demo123` 正常登录。
- 短密码注册或改密被拒绝。
- 改密后旧 token 失效。
- access token 过期后自动 refresh。
- refresh token 失效后回登录页。
- Docker 后端 + `pnpm run dev` 仅启动前端时可正常进入 `/dashboard`。

## 已知限制

- 匿名 `password-reset` 只能作为受控兼容方案存在，不再视为长期保留能力。
- Docker 本地演示环境与持久化生产环境的认证约束不同，后续实现时必须明确区分。
- 当前前端默认依赖 Docker 后端常驻，文档与脚本应围绕这一默认开发方式保持一致。
- 本文档记录的是优化顺序和验收目标，不等同于这些改动已经全部完成。
