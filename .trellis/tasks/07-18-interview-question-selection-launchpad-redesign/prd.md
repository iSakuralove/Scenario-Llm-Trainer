# 面试舱题目选择与启动体验重构

## 目标

把面试舱启动页从“选择聚合训练轨道”调整为“浏览并选择一条真实开场题”，让题目成为页面主体，用户能快速理解题目、按个人经历获得推荐，并在不反复设置的情况下开始面试。

## 用户价值

- 用户在进入面试前就能看到真实开场题，不再把题目集合误认为单道题。
- 用户可通过稳定题号截图、搜索和讨论某道题。
- 个人简历和项目经历只影响题库排序，不改变或生成题目。
- 面试设置只调整一次，切换题目时保持不变。
- 用户可在简历深挖模式中查看、切换并选择一份或多份简历，不必返回个人档案核对内容。

## 已确认事实

- 当前启动台卡片代表按领域和难度聚合的训练轨道，摘要会显示“前三个主题 + 等 N 题”，不是单道题。
- 当前新题库开场题来自已导入并发布的标准 JSON 题库。
- 当前标准 JSON、领域模型和导入链路只有 `title` 与 `subject`，没有独立的完整开场题干字段；运行时只能从 `title` 派生开场问题。
- 当前 `qb-mainstream-it-opening-20260718.json` 共 466 条，全部为 `opening`，`questionType` 全部为空，466 个标题全部使用“核心原理与适用场景”同一模板；现有内容实际上只有原理解释这一种主要形态。
- 面试入口规划为三类：用户自主选题的自由面试、未提供简历时按主流岗位方向开始的岗位专项面试、基于个人档案现有简历摘要与项目经历进行深挖的简历深挖面试。
- 当前页面会把设置区放在选中卡片之后，挤占题目列表空间；窄屏下还存在横向溢出。
- 当前卡片右上角普遍显示“选择题目”，选中后显示“已选择”。
- 当前个人档案只有单个 `resume_summary` 和 `project_summary` 字符串，没有多份简历实体、简历列表或解析状态；导入新文件会覆盖现有简历摘要。
- 当前简历导入只接受 `.txt`、`.md`、`.docx`、`.pdf`，不接受旧版 `.doc`；上传后只提取文字并写入个人档案，原文件、原文件名和格式信息不会保存。
- 当前后端已有通用资产元数据、用户资产列表和本地文件存储能力，但实际上传校验与存储路径仅覆盖语音资产；简历原文件需要复用并扩展该能力，不能继续只保存提取结果。
- 当前前端已有安全的 `MarkdownPreview` 与支持预览、编辑、导入和全屏的 `MarkdownComposer`，文本类简历无需新增另一套 Markdown 编辑器。
- 当前创建面试会话的接口不接收简历标识或简历摘要，简历内容尚未进入面试开场上下文；启动台推荐只读取个人档案中的偏好领域。
- 因此原型中的“选择一份或多份简历”不是现有能力的界面调整，而是需要新增存储、导入管理和面试上下文接入的跨层能力。

## 已确认需求

### 题目列表

- 标准 JSON 为 `opening/mixed` 题目新增独立的 `openingQuestion` 字段；`subject` 继续表示稳定考察点，`title` 继续表示展示标题，`openingQuestion` 表示真正向用户提出的完整第一问。
- 标准 JSON 新增受控枚举 `questionType`，用于在题目卡片展示“原理问答”“架构设计”等题型；不得继续把全部新题硬编码成同一种题型。
- `questionType` 首期固定为四种：`principle`（原理问答）、`troubleshooting`（故障排查）、`architecture`（架构设计）、`behavioral`（行为面试）。
- 简历深挖属于面试模式，不属于题库题型；不得增加为 `questionType`。
- 新题型只有在出现一批无法合理归入现有四类的导入题目时才扩展，并需同步更新统一枚举、导入校验、API 和前端筛选。
- 当前 466 道同模板题优先按真实内容清洗为上述题型，不通过增加空分类掩盖内容同质化。
- 自由面试和岗位专项面试使用题库中已导入并发布的 `openingQuestion`；简历深挖不依赖题库 `openingQuestion`。
- 新导入的 `opening/mixed` 题目必须包含非空 `openingQuestion`；旧数据允许在迁移期回退现有规则。
- `openingQuestion` 最长 50 个字符，超过上限时导入校验报错；卡片完整展示题干，不使用省略号或展开操作隐藏内容。
- 启动页展示真实、已发布且可作为开场题的题目，不再展示聚合轨道摘要。
- 卡片主文案直接展示真实开场题干，最多三行；不得再显示“主题 A · 主题 B · 主题 C 等 N 题”。
- 卡片下方只展示三个标签：领域、难度、题型。
- 题型使用面向用户的名称，例如“原理问答”“架构设计”。
- 卡片不使用随排序变化的 `01/02/03` 列表序号。
- 每道题展示稳定题号，格式为“领域缩写 + 永久数字编号”，例如 `AI-027`。
- 稳定题号可被搜索，且不得随推荐排序、搜索或筛选变化。
- 稳定题号在首次发布时确定，后续编辑领域也不得修改；如果题目归类发生根本变化，应归档旧题并发布新题。
- 未选中卡片右上角不显示任何操作文案。
- 选中卡片右上角只显示 `√`，不显示“选择题目”或“已选择”。
- 整张卡片可点击，同时支持键盘操作和可访问的选中状态。

### 推荐与排序

- 题目列表提供 `推荐｜未练过｜最新｜全部` 排序入口，默认使用“推荐”。
- 推荐排序优先使用用户的个人简历摘要和项目经历匹配已发布题目。
- 简历匹配之后再参考目标岗位、历史薄弱项、未练习题目和最近更新。
- 简历只参与现有题库的筛选和排序，不生成、不修改题目。
- 页面只显示“推荐”，不显示“简历匹配”“已按个人经历排序”等解释文案或徽章。
- 没有简历时自动降级到目标岗位、历史表现、未练习和最近更新等已有信号。

### 搜索与筛选

- 搜索支持题干、知识点、领域和稳定题号。
- 筛选维度为领域、难度、题型。
- 桌面端把搜索、领域、难度、题型合并为一行紧凑工具栏。
- 移动端只常驻搜索框和筛选图标，其他筛选放入底部筛选面板。
- `推荐｜未练过｜最新｜全部` 在桌面端和移动端均保持可见。
- 没有激活筛选条件时不显示“清空筛选”。
- 搜索、筛选或排序后，如果已选题目不再出现在当前结果中，自动取消选择并禁用“开始面试”；已设置的面试方式和轮数继续保留。

### 面试设置

- 常用设置以紧凑栏展示，包括面试方式、最大作答轮数、智能收束。
- 智能收束旁只显示“由面试官判断”；`1–15` 轮上限继续作为底层规则执行，不在该设置项旁展示。
- 重点追问等低频设置放入“更多设置”。
- “更多设置”随当前面试模式变化，不使用一套固定内容覆盖三种模式。
- 桌面端“更多设置”不得重复主页面已有的面试方式、轮数和智能收束；移动端“调整”面板需同时包含这些基础设置。
- 岗位专项的高级设置包括：目标级别（实习/初级/中级/高级）、随岗位变化的受控技术范围、面试重点（基础原理/项目实战/故障排查/架构设计）和可选岗位要求关键词。
- 技术范围由每个岗位维护受控选项；选择岗位时默认选中该岗位全部技术范围，用户可取消不需要的方向。
- 简历深挖的高级设置只提供“深挖重点”：项目职责、技术决策、难点与故障、性能与优化、协作与推动、结果与复盘；默认全部选中，用户可取消不希望追问的方向。
- “深挖重点”始终至少保留一项；只剩一项时不得继续取消，不增加“全部取消”或额外的“不限”状态。
- 简历深挖不复用岗位专项的目标级别、技术范围或岗位要求输入；简历内容决定问题范围，深挖重点只调整关注方向。
- 设置与题目选择解耦：用户调整一次后，切换题目不得重置。
- 桌面端紧凑展示常用设置；移动端常驻设置摘要，需要修改时打开底部面板。
- 设置区不得重复完整题干。

### 开始面试

- 删除现有页头中的“技术面试舱”“选择一道题，开始真实追问”和辅助说明。
- 在原页头位置放置“开始面试”主按钮，复用项目现有主按钮视觉样式。
- 首次进入页面时不默认选中题目。
- 未选择题目时按钮为灰色禁用状态。
- 点击题目卡片后按钮激活。
- 点击题目卡片只负责选中，不立即创建会话。
- 点击已激活的“开始面试”按钮后才创建会话并进入面试。

### 面试模式

- 三种模式共用 `/interviews` 页面，通过顶部 `自由选题｜岗位专项｜简历深挖` 分段控件切换，不新增独立模式选择页。
- 页面默认进入“自由选题”。
- 切换模式时分别保留已选题目、岗位方向和共用面试设置，不因切换而重置。
- “开始面试”按钮始终位于同一页头位置，并根据当前模式是否完成必要选择决定禁用或激活。
- 自由面试：用户自主浏览并选择具体题目后开始。
- 岗位专项面试：用户没有简历时选择主流岗位方向，例如 Python 工程师、Java 全栈工程师、爬虫工程师、大模型算法工程师，再由系统进入对应题库流程。
- 岗位方向列表提供搜索，按岗位名称和该岗位的受控技术范围匹配；没有匹配结果时显示空状态，不改变已经选中的岗位。
- 岗位专项面试开始前不展示系统选中的具体开场题；用户点击“开始面试”后，系统才从岗位匹配题库中选取 `openingQuestion` 并正式提问。
- 简历深挖使用独立的简历文档组成候选人上下文；文件上传不得再覆盖已有简历，个人档案中手动填写的简历摘要与项目经历作为一份可编辑的“手动填写”文档参与同一流程。
- 每份简历文档至少记录稳定 ID、名称、来源类型、文件格式、原文件资产、可编辑内容、提取文本、解析状态、质量状态和更新时间；文本类文档不要求同时保存重复的二进制副本。
- 用户可为本场面试选择一份或多份质量合格的简历，不要求指定主简历；至少选择一份后“开始面试”才可用。
- “当前查看的简历”和“本场已选择的简历”是两个状态：点击文件名只切换阅读内容，勾选状态才决定是否进入本场候选人上下文，避免用户为了查看文件而意外改变面试范围。
- 桌面端简历深挖内容区采用文档工作区：左侧为紧凑文件栏，右侧为当前简历阅读区；移动端把文件栏收纳为顶部文件选择菜单，不并排挤压正文。
- 文件栏显示简历名称、格式、质量状态和本场勾选状态；不使用大卡片列表。文件数量较多时文件栏独立滚动，正文位置不得随切换发生大幅跳动。
- 阅读区占用设置区下方的剩余可视高度并独立滚动，不把完整简历纵向铺满整个页面，也不再提供“查看完整内容”按钮或二次弹窗。
- PDF 以原文件只读预览；Word 类文件先生成安全的只读预览再展示，原文件仍保留；PDF、Word 等非纯文本文件不显示“编辑”按钮。
- Markdown、纯文本和“手动填写”文档统一按 Markdown 安全渲染并显示“编辑”按钮；进入编辑后在同一阅读区切换为编辑器，保存或取消后返回渲染视图。
- “手动填写”文档渲染时以“简历摘要”和“项目经历”作为固定内容分区，原始字段仍分别保存，不把两段内容不可逆地拼成一个字段。
- 纯文本没有 Markdown 标记时仍保留换行与段落，正文行宽控制在约 `65–75` 个字符、使用舒展行高和段落间距；不得为了展示效果自动改写、删减或重排用户经历。
- 内容较短时余白保留在稳定的阅读画布内部，文件栏和页面其他区域高度不随内容长度变化；内容较长时只滚动阅读区。
- 简历深挖的首个正式问题定义为“简历首问”，根据个人档案中的候选人上下文动态提出，不来自标准 JSON 的 `openingQuestion`。
- 任一已选择文档具有可用内容且通过内容质量校验，即可形成候选人上下文并开始简历深挖；“手动填写”文档仍允许简历摘要与项目经历只填写其中一项。
- 没有简历文档或没有选择质量合格的文档时，简历深挖模式保持可见，但“开始面试”禁用；内容区显示简短原因和“完善个人档案”入口。
- 无简历内容时不生成通用问题、不自动切换到岗位专项，也不把其他模式的问题伪装成简历深挖。
- 简历内容为空或未通过质量校验时，“开始面试”保持禁用且不响应点击；页面只显示简短原因和“完善个人档案”入口。
- 候选人上下文包含多个项目时，不增加“主项目”选择；系统按深挖重点、项目内容完整度和经历相关性选择一个具体项目提出单点简历首问。
- 具体项目中缺少候选人职责等必要信息时，简历首问先确认其实际负责内容，不直接假设其参与范围。

### 简历内容质量

- 文件导入和手动编辑简历摘要、项目经历都必须执行后端内容质量校验，前端校验只能用于即时提示，不得作为唯一防线。
- 明显与简历无关、有效信息过少、主要由重复或无意义文本组成的内容不得写入个人档案，也不得成为简历深挖上下文。
- 文件导入与手动保存必须复用同一套质量判定规则，避免同一内容因入口不同得到不同结果。
- 内容被拒绝时保留用户原有个人档案，不得用不合格内容覆盖已有简历摘要或项目经历。
- 个人档案保存或导入是主质量门槛：在写入前执行硬校验，不合格内容直接拒绝进入数据库。
- 开始简历深挖时复用同一规则做兜底复核，仅用于拦截历史遗留或绕过写入门槛的数据，不建立第二套判断标准。
- 开始阶段发现候选人上下文不合格时，禁用“开始面试”并引导返回个人档案；不在面试启动页弹出简历优化窗口。
- 硬过滤采用高精度拒绝策略，只拦截能够明确判定为无效的内容，例如有效文字过少、大量重复、主要由符号组成或完全不含经历、技能、职责、项目等简历信息。
- 简短但可能真实的边界内容允许保存，简历首问可先补充必要信息；不得为了追求拦截率误伤非常规或精简简历。
- 大模型不得作为拒绝写入或禁止面试的唯一裁决者；本期不为简历打主观质量分，也不自动重写用户内容。
- `resume_summary` 与 `project_summary` 中每个非空字段先分别执行清洁检查，拦截该字段自身的重复、符号堆积和明显无关内容。
- 字段清洁检查通过后，再合并两个字段判断候选人上下文是否具有足够的有效信息；允许只填写其中一个字段。
- 一个正常字段不得掩盖另一个字段中的明显垃圾内容，整体字数达标也不能跳过逐字段清洁检查。
- 合并后的候选人上下文至少包含 `60` 个有效字符；有效字符只统计 Unicode 字母和数字，不把空白与标点计入长度。
- 合并后的候选人上下文至少命中两类简历信息：经历/岗位、技能、项目/职责、成果、教育。
- 任一非空字段中符号占比或重复片段占比达到 `60%` 时，判定该字段清洁检查失败并拒绝保存。
- 每份简历文档先独立执行内容质量校验；本场选择多份简历时，再对合并后的候选人上下文去重并做兜底可用性判断，一份正常简历不得掩盖另一份明显垃圾文件。
- 合格但内容较长的简历不得仅因篇幅过长被拒绝；展示层通过阅读区滚动控制长度，面试上下文通过项目识别、去重和单点首问控制信息量。

### 响应式与状态

- 页面沿用项目现有的深色科技视觉语言与工作型信息密度，不为本次改造切换成儿童化、玩具化、黏土化或营销落地页风格。
- 新增的简历文件栏、阅读区和编辑态必须复用现有颜色、边框、按钮与交互反馈，不另起一套视觉体系。
- 题目列表获得页面主要空间；桌面端根据可用宽度显示多列，移动端单列。
- 页面在 320px 宽度不得产生横向滚动。
- 桌面文件栏不挤占正文的可读行宽；移动端文件选择菜单、编辑操作和开始按钮均可在 320px 宽度完成操作。
- 切换简历时阅读区回到顶部并更新名称、格式、质量状态和是否可编辑；动态更新需向辅助技术播报。
- 题目、推荐、筛选和历史数据需保留加载态、空状态和错误态。
- 禁用、选中、悬停和键盘焦点状态必须可辨识，不能只依赖颜色表达。

## 验收标准

- 页面首次加载时没有默认选中题目，“开始面试”按钮不可用。
- 选择任意题目后，仅该卡片右上角显示 `√`，按钮立即可用。
- 切换题目后面试设置保持不变。
- 每张卡片显示真实题干、稳定题号以及领域、难度、题型三个标签。
- 题干超过 50 个字符的导入项校验失败；通过校验的题干在卡片中完整可见。
- 页面和卡片中不再出现“等 N 题”“选择题目”“已选择”等旧文案。
- 默认“推荐”排序优先返回与简历/项目经历相关的已发布题目；无简历时正常降级。
- 搜索可通过稳定题号命中对应题目。
- 桌面端筛选为紧凑单行；移动端筛选进入底部面板。
- 320px、768px、1024px、1440px 下无横向溢出、文字遮挡或不可操作控件。
- 键盘可完成题目选择并触发已启用的开始按钮。
- 简历深挖可展示并切换多份独立简历；上传新文件不会覆盖已有文件，手动填写内容作为可编辑文档出现在同一文件栏。
- 没有简历文档或没有选择质量合格的简历时，简历深挖的开始按钮不可用，并可通过“完善个人档案”进入现有档案页面。
- 点击文件名只切换当前预览，勾选或取消勾选才改变本场候选人上下文；至少保留一份质量合格的已选简历才能开始。
- PDF 与 Word 类文件显示只读预览且没有编辑入口；Markdown、纯文本和手动填写内容安全渲染 Markdown，并可在同一阅读区进入编辑、保存和取消。
- 简历工作区不显示“查看完整内容”；长内容只滚动阅读区，短内容的余白留在阅读画布内部，文件栏与页面主体高度稳定。
- 简历内容为空或质量不合格时，禁用的开始按钮没有点击反馈，旁边或内容区提供简短原因提示。
- 个人档案中的简历摘要或项目经历任一项非空且通过质量校验时，简历深挖可以开始。
- 文件导入与手动保存遇到明显无效的简历内容时均返回可操作的错误，原有档案内容保持不变。
- 历史档案中的不合格内容不能绕过校验开始简历深挖；页面引导用户返回个人档案修改，不弹出优化简历对话框。
- 简短但包含真实简历信息的内容不会仅因篇幅短被拒绝；相同的明显垃圾内容不能因模型输出波动而时而通过、时而失败。
- 每个非空字段均通过清洁检查且合并后的候选人上下文通过可用性判断时，才能保存并用于简历深挖；其中一个字段为空不构成失败。
- 少于 `60` 个有效字符、未达到两类简历信息，或任一非空字段的符号/重复片段占比达到 `60%` 时，后端拒绝写入且不覆盖原档案。
- 简历包含多个项目时界面不出现“主项目”设置；简历首问锚定一个具体项目，职责信息不足时先提出澄清问题。
- 简历深挖的六项重点默认全选且至少保留一项，任何交互路径都不能产生零项选中的状态。
- 简历达到数千字或包含大量项目时，页面主体不随正文无限增高，正文行宽保持可读，阅读区可滚动且页面无横向溢出。

## 暂不包含

- 在启动页调用 AI 临时生成题目。
- 修改导入题目的正文内容。
- 改造历史面试和面试报告页面。
- 新增独立推荐说明区或简历匹配徽章。
- 为本次改造创建新的视觉设计系统或外部依赖。

## 已确认补充

- 纯文本和 Markdown 采用文档工作区，不把完整正文铺成页面级长文。
- 首期 Word 文件只支持 `.docx`；旧版 `.doc` 在具备稳定、安全的转换链路前不接收。
